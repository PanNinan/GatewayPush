## 1. 工具链全貌

### 1.1 四种切面，不是四道工序

四套工具跑的是**同一份源码**，但观察维度不同：

| 工具 | 观察维度 | 数据基础 | 会写文件 | 配置文件 |
|---|---|---|---|---|
| **php-cs-fixer** | 文本形态 | `token_get_all()` 产出的 token 流 | ✅ 仅 `composer cs` | `.php-cs-fixer.dist.php` |
| **php_codesniffer** | 文本形态 | 富 token（带行列号、括号嵌套、关联 token） | ❌ 只读 | `phpcs.xml.dist` |
| **PHPStan** | 语义与类型 | AST + 符号表 + 类型推断 | ❌ 只读 | `phpstan.neon` |
| **phpstan-phpunit** | 测试代码的语义 | 挂在 PHPStan 上的扩展 | ❌ 只读 | 被 `phpstan.neon` include |

能力是递进的，可以这样理解这条链：

| 层次 | 能判断 | 不能判断 |
|---|---|---|
| token 流 | 缩进错、引号风格不一致、`array()` 该换 `[]` | 「这个变量是 int 还是 string」 |
| 类型模型 | 「你把 `mixed` 传给了要求 `string` 的形参」 | 「这段代码运行时会真的走到」 |
| 执行测试 | 「这个分支算错了、这个边界没覆盖」 | 无法穷举，只能覆盖 |

## 2. php-cs-fixer —— 排版（唯一写文件）

### 2.1 工作原理

1. `token_get_all()` 把整个文件切成 token 数组 —— **不做 AST 解析**
2. 每条 fixer 声明自己关心的 token 类型，并**改写 token 数组**
3. 引擎把改后的 token 拼回文本
4. **再跑一轮**，直到不再产生变化（固定点迭代）

由此推出三条推论，决定了它能干什么：

- 它**不理解类型、不理解控制流**。它看到的是「`T_STRING` + `T_VARIABLE`」，不是「string 传给了 int 形参」
- 它**只看语法形态**，所以「空白 / 缩进 / 换行 / 括号 / 引号 / 标签顺序」是它的主场
- 因为改的是 token，**不会误伤字符串内部**（`"a  b"` 里的双空格不会被空白类规则动到）

### 2.2 规则集构成

```php
->setRiskyAllowed(true)
->setRules([
    '@auto' => true,        // @PER-CS + 按 composer.json 的 PHP 下限推导的迁移规则
    '@auto:risky' => true,  // 现代写法迁移
    '@PhpCsFixer' => true,  // 项目级排版细则（= @PER-CS + @Symfony + 额外项）
] + $boundary)
```

**`@auto` 的迁移目标由 `composer.json` 的 PHP 下限决定，不是运行时版本。**
它展开为 `@PER-CS` + `@autoPHPMigration`（该子集再按下限取 `@PHP81Migration` / `@PHP82Migration` …）。

> ⚠ **下限一改，这里展开的规则集就跟着变** —— 上调 PHP 下限后必须重跑
> `composer cs:check`，确认没有新引入自动改写。
> 2026-09-22 由 8.1 抬到 8.2 后实测仍为 **`0 of 120 files`**，即现有代码无需因下限提升而改写。
> 不过它与 `composer.json` 绑定这一点必须记住：抬下限不只是改一个数字。

`setRiskyAllowed(true)` 是必需的：`@auto:risky` 里的 `modernize_strpos`（`strpos() !== false` → `str_contains`）、
`use_arrow_functions`（`function () {}` → `fn ()`）、`no_alias_functions` 都属 risky 集。
真正会改语义的项都在 `$boundary` 里逐条关掉（见 2.4）。

### 2.3 扫描范围（Finder）

```php
->in([__DIR__ . '/src', __DIR__ . '/client', __DIR__ . '/config', __DIR__ . '/tests'])
->append([__DIR__ . '/start.php'])
->name('*.php')
```

> ⚠ **不要写成 `->in(__DIR__)`**。`runtime/phpstan/` 下有 800+ 个分析器生成文件，
> 实测会把 118 个源文件放大成 **1011 个**，全量 dry-run 直接跑不完（曾卡死 4 分 56 秒后超时）。

### 2.4 四个界外：23 条显式关闭的规则

判据只有一条 —— **越界即长期噪声**。`$boundary` 共 23 条，分四类。

#### 界外①：注释内容归 phpcs（9 条）

| 规则 | 不关会怎样 |
|---|---|
| `phpdoc_to_comment` | 把行内 `@var` 注解降级成普通注释 —— **PHPStan 直接失明** |
| `phpdoc_summary` | 给中文摘要补英文句点：「…读取」→「…读取.」 |
| `phpdoc_add_missing_param_annotation` | 自动补 `@param`：注释「有没有」不该由排版工具决定 |
| `no_superfluous_phpdoc_tags` | 删 `@param` / `@return`，与 phpcs 的完整性审计对撞 |
| `phpdoc_no_empty_return` | 删 `@return void` |
| `phpdoc_no_useless_inheritdoc` | 删 `@inheritDoc` |
| `phpdoc_var_without_name` | 删 `@var Foo $bar` 里的 `$bar` —— 属「删除注释内文字」 |
| `php_unit_internal_class` | 给测试类补 `@internal`：属「新增注释内容」 |
| `php_unit_test_class_requires_covers` | 补 `@covers`：新增注释内容，且改动 PHPUnit 覆盖率语义 |

#### 界外②：运行语义 / 类型声明（4 条）

| 规则 | 不关会怎样 |
|---|---|
| `declare_strict_types` | 它按**调用方文件**生效。逐文件加会让同一函数在不同调用点行为不一致（非严格模式自动 `int→string`，严格模式抛 `TypeError`）。本项目下限 8.2、兼容 8.2~8.5，依赖 workerman 生态的宽松转换 |
| `random_api_migration` | `mt_rand()` → `random_int()`：**熵源与失败行为都变了**，不是排版 |
| `void_return` | 补 `: void` 是**新增原生类型声明** —— 该动作应发生在独立的类型补全任务（须同步接口/实现），不该由排版工具顺手落盘；且会与 phpcs 的 `@return` 审计交叉 |
| `protected_to_private` | **改可见性 = 改语义**。静态分析若漏判外部继承即破坏扩展点 |

#### 界外③：保留项目既有压倒性约定（6 条，均带实测数据）

| 规则 | 设为 | 既有现状 | 不关会怎样 |
|---|---|---|---|
| `concat_space` | `one` | `' . '` **947 处 : `'.'` 0 处** | 全量反转 |
| `binary_operator_spaces` | `at_least_single_space` | 赋值号对齐 **78/117 文件、467 行** | 对齐全部打散 |
| `cast_spaces` | `none` | `(string)$x` **752 : 2** | 全量加空格 |
| `increment_style` | `post` | `$i++` **36 : 1** | 全量改前置 |
| `blank_line_after_opening_tag` | `false` | **117/117 文件** `<?php` 紧贴 | 全量插空行 |
| `no_blank_lines_after_phpdoc` | `false` | 文件头注释与代码之间保留空行 | 全量删空行 |

> ⚠ **`concat_space` 必须手写设回 `one`**：`@Symfony` 里用 `'concat_space' => true`
> **显式覆盖**了 `@PER-CS` 的 `one`（vendor 源码注释写着 `overrides @PER-CS2.0`），默认值是 `none`。
> 不显式设回，项目 947 处 `' . '` 会被一次性反转。

#### 界外④：结构 / 工具层不该插手（4 条）

| 规则 | 不关会怎样 |
|---|---|
| `fully_qualified_strict_types` | `@PhpCsFixer` 给它配了 `import_symbols: true` —— 会**自动新增 `use` 语句**并把 FQCN 缩短成短名。`start.php` 同时引用 4 个同名 `Bootstrap`，只给其中一个加 `use` 反而更难读 |
| `global_namespace_import` | 同类：也会自动新增 `use Foo\Bar;` 把 FQCN 换成短名 |
| `yoda_style` | `@Symfony` 默认 `true`，会把 `$x === 0` 全改成 `0 === $x` |
| `line_ending` | 行尾统一交给 git —— **本条待重估，见 §8.5** |

### 2.5 运行方式与只读体检

```bash
composer cs:check   # dry-run + diff，只报不改
composer cs         # 落地（已内置 --sequential）
```

两条容易踩的选项：

- **`--sequential` 不能省**：并行模式下子进程会超时（`Child process timed out after 120 seconds`）。
  顺序模式实测 118 文件约 16 秒，完全够用。
- **想看「到底应用了哪些 fixer」必须加 `-v`**：`ReportSummary::shouldAddAppliedFixers()`
  要求 verbosity ≥ `VERBOSE`，否则 JSON 报告里的 `appliedFixers` 是空数组。

### 2.6 已知坑位

| 现象 | 根因 / 处置 |
|---|---|
| `--dry-run` 空输出 + 卡死数分钟 | Finder 用了 `->in(__DIR__)`，扫进 `runtime/phpstan/` 生成产物（118 → 1011 文件） |
| 配置文件语法错误 `unexpected token "`"` | 块注释里写了 `*/` 字面量（例如想描述行内 `@var` 注解时），注释被提前闭合 |
| 全量 dry-run 与单文件结果不一致 | 结果缓存。加 `--using-cache=no` 复现 |

## 3. php_codesniffer —— 审计（只读）

### 3.1 工作原理

1. PHPCS 自带的 tokenizer 产出**富 token 流**（带行号、列号、括号嵌套层级、关联注释）
2. 每个**嗅探器（Sniff）** 用 `register()` 声明它关心的 token 类型
3. PHPCS 遍历文件，只在命中的 token 位置回调 `process()`
4. 嗅探器用 `addError()` / `addWarning()` 累积报文
5. 退出码由「是否有 error / 是否可自动修」决定（见 3.4）

**本项目只用它做只读审计**，不使用 `phpcbf`（写回工具）。原因见 §6.4。

### 3.2 为什么不挂整包标准

`phpcs.xml.dist` **不写 `<rule ref="PSR12"/>`**，也不挂 Squiz / Zend 整包，而是逐个点名嗅探器。

理由：PSR12 / Squiz 这些整包里**过半是排版类嗅探器**，一挂就会与 php-cs-fixer 抢同一批代码，
形成「A 报 B 修」的长期噪声。逐个排除单码要写十几条 `<exclude>`，还不如直接点名。

代价：新增检查必须显式加进规则集，不会随基础标准升级自动获得。这是有意接受的取舍。

### 3.3 生效的 35 个嗅探器

36 条 `<rule ref>` 条目（其中 `Squiz.Commenting.FileComment.Missing` 是对 `FileComment` 嗅探器内单个码的引用），
去重后 **35 个嗅探器**：

| 标准 | 数量 | 嗅探器 |
|---|---|---|
| Squiz | 17 | `Commenting.FileComment` / `Commenting.ClassComment` / `Commenting.FunctionComment` / `Commenting.FunctionCommentThrowTag` / `Commenting.VariableComment` / `Commenting.EmptyCatchComment` / `Classes.ValidClassName` / `NamingConventions.ValidFunctionName` / `NamingConventions.ValidVariableName` / `Scope.MethodScope` / `Scope.MemberVarScope` / `Scope.StaticThisUsage` / `PHP.Eval` / `PHP.GlobalKeyword` / `PHP.InnerFunctions` / `PHP.NonExecutableCode` / `PHP.DisallowSizeFunctionsInLoops` |
| Generic | 13 | `Commenting.Todo` / `Commenting.Fixme` / `NamingConventions.UpperCaseConstantName` / `NamingConventions.ConstructorName` / `CodeAnalysis.AssignmentInCondition` / `CodeAnalysis.EmptyStatement` / `CodeAnalysis.JumbledIncrementer` / `CodeAnalysis.RequireExplicitBooleanOperatorPrecedence` / `CodeAnalysis.UnusedFunctionParameter` / `PHP.DisallowShortOpenTag` / `PHP.DeprecatedFunctions` / `Metrics.CyclomaticComplexity` / `Metrics.NestingLevel` |
| PSR1 | 2 | `Classes.ClassDeclaration` / `Methods.CamelCapsMethodName` |
| PSR2 | 1 | `Classes.PropertyDeclaration` |
| GatewayPush（自定义） | 2 | `ForbiddenCallSniff` / `RedisKeyLiteralSniff` |

复杂度与嵌套两条（`CyclomaticComplexity` / `NestingLevel`）**设为 warning** ——
阈值属团队决策，先作提示，不卡门禁。

### 3.4 退出码语义

PHPCS 4.0 起退出码改为**位标志**（`src/Util/ExitCode.php`）：

| 值 | 常量 | 含义 |
|---|---|---|
| 0 | `OKAY` | 全通过 |
| 1 | `FIXABLE` | 全是可自动修的错（本项目不用 phpcbf，实际不会出现） |
| 2 | `NON_FIXABLE` | 存在不可自动修的错 —— **门禁关注的就是这个** |
| 4 | `FAILED_TO_FIX` | phpcbf 修了但没修好 |
| 16 | `PROCESS_ERROR` | 处理过程出错 |
| 64 | `REQUIREMENTS_NOT_MET` | 运行环境不满足 |

项目用 `<config name="ignore_warnings_on_exit" value="1"/>` 让 **warning 不影响退出码** ——
于是 `composer lint` 的退出码语义收敛成一句话：**只有 error 会让门禁变红**。

> ⚠ 其余运行时配置项（`ignore_errors_on_exit` 等）在 ruleset 里写 `<config>` 对 PHPCS 4.0.4 **无效**，
> 必须命令行 `--runtime-set`。`ignore_warnings_on_exit` 之所以生效，是因为它是 `Config` 的既有属性。

### 3.5 自定义红线嗅探器

`tools/phpcs/Sniffs/` 下两个嗅探器，把「只写在文档里的红线」变成机器可查：

| 嗅探器 | 守什么 | 为什么不能靠内置嗅探器 |
|---|---|---|
| `PHP/ForbiddenCallSniff` | `src/`、`client/src/` 内禁止 `exit` / `die` / `sleep` / `usleep` / `pcntl_fork` | `Generic.PHP.ForbiddenFunctions` **抓不到 `exit` / `die`** —— 它们是 `T_EXIT` **语言结构**，不是函数调用 |
| `Common/RedisKeyLiteralSniff` | 禁止 Redis 键名硬编码，必须引用 `RedisKeys::` | 内置无此能力 |

两条关键实现约定：

**① 作用域与豁免写在嗅探器属性里**（`$filePattern` / `$exempt`），不写在 `phpcs.xml.dist` 里。
因为**按文件路径引用嗅探器时，规则级 `include-pattern` / `exclude-pattern` 会静默失效**：
`Ruleset::processRuleset()` 在 `$code === $ref`（即 ref 是路径字符串）时把模式注册到「路径字符串」这个键下，
而检查时 `File` 按嗅探器编码（如 `gatewaypush.php.forbiddencall`）取值，模式永远不命中。

豁免情形：

| 嗅探器 | 豁免文件 | 理由 |
|---|---|---|
| `ForbiddenCallSniff` | `client/src/Cli/Debugger.php` | CLI 调试器允许 `exit` |
| `RedisKeyLiteralSniff` | `src/Common/RedisKeys.php` | 键名真源，字面量就该写在这里 |

**② 自定义标准的命名空间由文件路径推导**：文件必须落在 `<Standard>/Sniffs/<Category>/<Name>Sniff.php`，
`Common::getSniffCode()` 取 `$parts[count-4]` 作 standard、`$parts[count-2]` 作 category。

> `RedisKeyLiteralSniff::$prefixes` 是 `RedisKeys` 常量的**手写副本** ——
> 新增 Redis 键后忘记同步，红线就静默失效。
> 所以配了自检：`composer lint:self` 用反射枚举 `RedisKeys` 的全部字符串常量，逐一比对是否被 `$prefixes` 覆盖；
> 同时用 6 条路径跑作用域/豁免矩阵（`src/` = 全查、`start.php` = 不查、`Debugger.php` = 只查键名、`RedisKeys.php` = 只查禁则）。

### 3.6 四类刻意排除

> 与 `phpcs.xml.dist` **文末四个「刻意排除」注释块**一一对应（真源以该文件为准）。
> 另有若干**规则体内的单码排除**（`@inheritDoc` / 框架属性访问等）写在各 `<rule ref>` 下方，
> 不计入文末四类，见本节末「附」。

调优过程：**6297 → 412 → 253 → 192 → 0 errors**。

#### ① 与 php-cs-fixer 重叠（归 fixer 管，含 long form 子项）

`PSR12.Properties.ConstantVisibility` / `Squiz.Operators.ValidLogicalOperators` /
`Generic.Arrays.DisallowLongArraySyntax` / `Generic.PHP.LowerCaseConstant` /
`Generic.PHP.LowerCaseKeyword` / `Squiz.Commenting.DocCommentAlignment` /
`Squiz.Commenting.{LongConditionClosingComment,ClosingDeclarationComment,PostStatementComment}` /
Squiz 与 Generic 的 `WhiteSpace.*`。

**long form 子项**：Squiz 处处用 **long form**（`integer` / `boolean`）比对类型，
fixer 的 `phpdoc_scalar` 统一改成 short form（`int` / `bool`），**两个工具会无限来回修**。
涉及：`Squiz.Commenting.VariableComment.IncorrectVarType`、
`Squiz.Commenting.FunctionComment.{IncorrectParamVarName,InvalidReturn}`。

#### ② 英文散文体例（对中文注释全是误报）

| 排除项 | 原报数 | 误报原因 |
|---|---|---|
| `Generic.Commenting.DocComment` | ~1750 | tag 值缩进 804、tag 分组空行 422、短描述缺失 135、`/**` 后换行 262…（其中「分组空行」正是 fixer 的 `phpdoc_separation`） |

## 4. PHPStan —— 静态类型分析

### 4.1 工作原理

不执行代码，做三件事：

1. **建符号表** —— 所有类 / 方法 / 函数 / 常量的签名（含 `vendor/` 的 stub）
2. **类型推断** —— 沿控制流推导每个表达式可能的类型集合（联合类型、泛型、交叉类型）
3. **按规则断言** —— 拿「类型信息 + 语法结构」比对规则

因为要**跨文件**建全量模型，PHPStan 能回答「`Router::dispatch()` 第 2 个参数期望什么类型」——
这是 token 级工具做不到的。代价是慢，且**必须依赖结果缓存**。

### 4.2 参数逐条

| 参数 | 值 | 说明 |
|---|---|---|
| `level` | `6` | **2026-09-22 由 5 提升**。提级前量化：level 6 全量 **538 errors / 66 文件，100% 是 `missingType.*`**（`iterableValue` 330 / `return` 167 / `parameter` 34 / `property` 7），**零语义告警** —— 增量只是「数组元素类型标注完整性」，不含逻辑类检查。处置：生产侧 265 条补 phpdoc 清零，测试侧 273 条冻结进 `phpstan-tests-baseline.neon`。详见 4.3 |
| `paths` | `src` / `client/src` / `start.php` / `tests` / `client/tests` | **`tests` 必须在列**，否则 `phpstan-phpunit` 的断言 / mock 规则不会生效 |
| `phpVersion` | `80200` | 按**项目下限**（`"php": ">=8.2"`）推断语言特性，不跟随分析机版本。下限已抬到 8.2 后本机二者一致，但该锚点仍然必要：若将来在 8.3+ 上分析，8.3+ 才引入的类型仍会被判未知类型 —— **这是刻意的防呆**，提示不要把高版本文档 / 语法当作可依赖前提 |
| `treatPhpDocTypesAsCertain` | `false` | workerman 大量使用动态属性（`$worker->onMessage = ...`），不把 phpdoc 类型当作绝对事实 |
| `tmpDir` | `runtime/phpstan` | 结果缓存（已 gitignore）。**改代码后要 `clear-result-cache`**，否则缓存会掩盖既有错误 |
| `scanFiles` | 两个 phpcs 嗅探器 | 见 4.5 |
| `strictRules` | `allRules: true` + 4 项关闭 | 见 4.4 |
| `ignoreErrors` | workerman/redis 的 phpdoc 缺陷 | 其方法签名把回调参数标注为 `@param null $cb`，而运行期实际接受 `callable`。本项目全程强制「回调式调用」（`RedisClient` 的封装约定），属库侧问题，集中声明在此而不污染 baseline |

### 4.3 baseline 策略

**「baseline 冻结存量 + 新代码零容忍」**，且存量分成两份：

| 文件 | 范围 | 条目数 | 抑制告警数 |
|---|---|---|---|
| `phpstan-baseline.neon` | 生产代码 | 0（`ignoreErrors: []`，2026-09-23 清空） | 0 |
| `phpstan-tests-baseline.neon` | 测试侧 | 301 | 311（273 missingType + 38 语义） |

> 测试侧在 2026-09-22 提级时重新生成，**新增的 273 条全部是 `missingType.*`**
> （`return` 165 / `iterableValue` 68 / `parameter` 33 / `property` 7）。为何测试侧不跟着补：
> 测试替身补 `: void` 收益极低，且引入**原生返回类型会改变运行期行为**（返回值不符即 TypeError），
> 冻结比强修划算 —— **生产侧已于 2026-09-23 补齐属性与方法原生类型，测试侧刻意维持 phpdoc-only**。
> 这也是「两份 baseline」设计的价值所在 —— 稀释掉的只是测试部。
>
> **重新生成的四个前提**（少一步就会产出缺条目的 baseline）：
> ① `level` 先改到目标级别；② **临时注释掉两个 baseline 的 `includes`** ——
> 否则已冻结条目会先把错误吃掉；③ `--generate-baseline` 按 `parameters.paths` **全量**生成，
> 生产侧若有残留条目会一并写进来，需**剔除 `path` 不以 `tests/` / `client/tests/` 开头的条目**（2026-09-23 语义清洗后生产侧已清空，正常情况不会写出条目）；
> ④ 恢复 includes 后再跑 `composer analyse`，必须 0 errors 且 0 条 `ignore.unmatched`。
> 注意 `runtime/` 下的探针配置里 `paths` 是**追加**语义（Néon 列表合并），
> 想收窄范围只能新建独立配置或事后过滤，不能靠覆盖同名键。

分成两份是为了**只减不增**：测试侧的噪音不会混进生产代码的 baseline，
也就不会被误当成「生产代码的既有债务」而被顺手豁免掉。

> ⚠ **`level` 与 baseline 必须同源。**
> baseline 是用哪个 level 生成的，`parameters.level` 就得是哪个值。
> 不一致会触发成百上千条 `ignore.unmatched (non-ignorable)`，门禁直接红。
> **历史上真发生过一次**：baseline 以 level 6 重新生成（362 条），而配置仍是 level 5，
> 结果 351 条 unmatched 直接让 `composer analyse` 失败。

> ⚠ **不要用 `composer baseline` 重新生成生产代码基线** ——
> 它会把新引入的告警一起冻结进去，等于变相放弃零容忍。

#### baseline 有**两种**失效方式，都必须处置

| 失效方式 | 触发 | 表现 |
|---|---|---|
| **level 漂移** | baseline 用 A 级生成，`parameters.level` 是 B 级 | 成百上千条 `ignore.unmatched` |
| **条目失效（只增不减）** | 重构 / 批量修把真实告警修掉了，但 baseline 里对应条目没删 | 该条目报 `ignore.unmatched (non-ignorable)` |

> **2026-09-22 实例**：一批重构提交修掉了 11 条真实告警
> （`client/tests/E2E/ClientE2E.php` 的 3 个多余闭包 `use`、两个测试文件的 `assertSame(count())` → `assertCount()`、
> `tests/Manual/_p5_bind_check.php` 与 `src/Business/Auth.php` 的多余 `use`），
> 但两份 baseline 里的 7 个对应条目未同步删除 → `composer analyse` 报 **7 条 `ignore.unmatched`**、退出码 1、门禁变红。
> 处置：按「失效即删」剔除 7 个条目（生产 10→9、测试 57 条目/78 条 → 51 条目/67 条），恢复 `[OK] No errors`。
>
> **教训**：baseline 的「只减不增」不只是「不许加」，还包括「修好了就必须减」。
> 排查时若看到 `ignore.unmatched`，先问「最近有没有重构把某类告警修掉了」，而不是去怀疑 level 配置。

### 4.4 `phpstan-strict-rules` 的取舍

`allRules: true`，仅关以下 4 项：

| 关闭项 | 理由 |
|---|---|
| `disallowedEmpty` | `empty($x)` 换成 `!$x` **不是等价改写**：`empty('0') === true`，而 `!'0' === false`。全仓 96 处，机械替换会改运行时语义。（「键是否存在」的判定仍按项目红线用 `array_key_exists`） |
| `booleansInConditions` | 要求条件表达式严格布尔化。本仓大量 `if (!$row)` / `while ($list)` 这类「数组 / 集合真值判断」，改法牵动面大而收益有限 |
| `booleansInLoopConditions` | 同上 |
| `dynamicCallOnStaticMethod` | `$class::$method()` 正是 `Task` 与 `Router` 的反射分发设计本身（config 声明 → 反射调用），不是误用；开这条等于与设计对抗 |

实测（level 5，src+client 侧）：全开 **+187 条**，上述关闭项占 **157 条（84%）**；
关掉后其余规则只额外报 11 条，属可修的真问题。

### 4.5 已知坑位

| 现象 | 根因 / 处置 |
|---|---|
| 改了代码但分析结果不变 | 结果缓存。用 `php vendor/bin/phpstan clear-result-cache --memory-limit=512M`；**不要用 `rm -rf runtime/phpstan`**（本机安全策略对批量删除会直接拦截） |
| 报 `class.notFound`（4 条）指向 `tools/phpcs/Sniffs/*` | **phpcs 的 `composer.json` 没有 autoload 段**（它用自带的 `autoload.php`），两个嗅探器类不在 composer autoloader 里。解法是用 `scanFiles`（只做**符号发现**、不分析内容）而不是放进 `paths` —— 若放进 `paths`，嗅探器内部对 `PHP_CodeSniffer\*` 的引用会变成新告警 |

## 5. phpstan-phpunit —— 测试域的 PHPStan 扩展

### 5.1 它不是测试运行器

这是最容易误解的一点：**`phpstan-phpunit` 不跑测试**。

它是挂在 PHPStan 上的一个**扩展包**，作用是让 PHPStan「看懂」PHPUnit 的语义 ——
否则 `$this->assertInstanceOf()` 之后的类型收窄、`$this->createMock()` 的返回类型，
PHPStan 全都推不出来，测试代码会报一堆假阳性。

真正跑测试的是 **PHPUnit 9.6.36**（`phpunit.xml`）。两者分工见 5.4。

### 5.2 四类贡献

全部来自 `extension.neon` + `rules.neon`。

#### ① 7 个 stub 文件

`Assert.stub` / `AssertionFailedError.stub` / `ExpectationFailedException.stub` /
`MockBuilder.stub` / `MockObject.stub` / `Stub.stub` / `TestCase.stub`

PHPStan 不分析 `vendor/` 源码，靠 stub 给 PHPUnit 的类补上更精确的类型签名。

#### ② 3 个 typeSpecifyingExtension（断言驱动的类型收窄）

- `AssertFunctionTypeSpecifyingExtension`（`assertSame()` 函数形式）
- `AssertMethodTypeSpecifyingExtension`（`$this->assertSame()`）
- `AssertStaticMethodTypeSpecifyingExtension`（`self::assertSame()`）

有了它，下面这段才不会被误报 `method.notFound`：

```php
$this->assertInstanceOf(RedisClient::class, $client);
$client->ping();   // PHPStan 知道此处 $client 一定是 RedisClient
```

#### ③ 2 个 dynamicReturnTypeExtension

- `MockBuilderDynamicReturnTypeExtension`
- `MockForIntersectionDynamicReturnTypeExtension`

让 `$this->createMock(Foo::class)` 的返回类型推成 **`Foo&MockObject` 交叉类型**
（`getMockBuilder()` 同理）。这是 mock 能通过类型检查的前提。

#### ④ 22 个 PHPUnit 专项规则

`AssertSameWithCount` / `AssertSameBooleanExpected` / `AssertSameNullExpected` /
`AssertEqualsIsDiscouraged` / `MockMethodCall` / `DataProviderDeclaration` / `DataProviderData` /
`ShouldCallParentMethods` / `ClassCoversExists` / `ClassMethodCoversExists` /
`NoMissingSpaceInClassAnnotation` / `NoMissingSpaceInMethodAnnotation` /
`AttributeRequiresPhpVersion` / `ClassAttributeRequiresPhpVersion` …

#### 外加 3 条 PHPUnit 语义声明

| 配置 | 作用 |
|---|---|
| `additionalConstructors: TestCase::setUp` | 告诉 PHPStan `setUp()` 是构造期初始化点，属性在其中赋值不算「未初始化」 |
| `earlyTerminatingMethodCalls: Assert::fail / markTestIncomplete / markTestSkipped` | 这三个调用之后控制流**终止**，消掉不可达代码误报 |
| `exceptions.uncheckedExceptionRegexes: ^PHPUnit\` | PHPUnit 系异常视为已检查，不必逐个 `@throws` |

### 5.3 生效前提（最容易失效的地方）

**① 必须显式 `includes`。** 本项目**未装 `phpstan/extension-installer`**，所以 `phpstan.neon` 里手写三条：

```neon
includes:
    - vendor/phpstan/phpstan-strict-rules/rules.neon
    - vendor/phpstan/phpstan-phpunit/extension.neon
    - vendor/phpstan/phpstan-phpunit/rules.neon
```

> 只 `composer require` 不写 `includes`，**规则一条都不会生效**，而且不会报任何错。

**② `paths` 必须含 `tests` / `client/tests`。** 只装扩展不分析测试目录，等于白装。

### 5.4 与 PHPUnit 的分工

| | phpstan-phpunit | PHPUnit |
|---|---|---|
| 干什么 | 静态分析测试代码的**类型与写法** | **执行**测试代码，看运行行为 |
| 何时跑 | `composer analyse` | `composer test` |
| 能发现 | `createMock()` 返回类型错、`assertSame` 参数顺序错、data provider 声明错、`@covers` 指向不存在的类 | 逻辑分支算错、边界条件没覆盖、断言期望值写错 |
| 是否执行代码 | ❌ | ✅ |

两者互补，都要跑。

## 6. 职责边界

### 6.1 判据

唯一判据：**同一段代码会不会被两边「反向」修**。

- 会反向修 → 必须指派给**唯一**一方，另一方排除该码
- 只报告不修改 → 不构成冲突，可以多方都看

### 6.2 谁说了算

| 代码现象 | 负责方 | 依据 |
|---|---|---|
| 空白 / 缩进 / 换行 / 括号 / 引号 / `array()`→`[]` / `isset()?:`→`??` | php-cs-fixer | `array_syntax` 落盘前命中 95 文件 |
| phpdoc 标签**有没有** | phpcs | `FunctionComment.Missing` |
| phpdoc 类型写 `int` 还是 `integer` | php-cs-fixer | `phpdoc_scalar`；phpcs 侧 long form 相关码已排除 |
| 变量 / 方法 / 类命名 | phpcs | `ValidFunctionName` / `ValidClassName` |
| Redis 键名是否硬编码 | phpcs（自定义） | `RedisKeyLiteralSniff` |
| `exit` / `die` / `sleep` 是否出现在 `src/` | phpcs（自定义） | `ForbiddenCallSniff` |
| 传入类型对不对、方法存不存在 | PHPStan | `argument.type` / `method.notFound` |
| `empty()` 该不该用 | PHPStan strict-rules（**已关**） | 语义不同，机械替换会改行为 |
| `createMock()` 返回什么类型 | phpstan-phpunit | 动态返回类型扩展 |
| 断言之后变量类型是否收窄 | phpstan-phpunit | typeSpecifyingExtension |
| 行尾（CRLF / LF） | **git**（当前）+ 见 §8 | 两侧工具都不插手 |

### 6.3 三处真实冲突点（已处理）

| 冲突 | 表现 | 处置 |
|---|---|---|
| **long form ↔ short form** | Squiz 要求 `integer` / `boolean`，fixer 的 `phpdoc_scalar` 改回 `int` / `bool` | phpcs 侧排除 `IncorrectVarType` / `IncorrectParamVarName` / `InvalidReturn` 三个码 |
| **`concat_space`** | `@Symfony:53` 的 `'concat_space' => true` 覆盖 `@PER-CS` 的 `one`，默认 `none`，与项目 947:0 相反 | fixer 侧显式设回 `one` |
| **`@inheritDoc`** | fixer 的 `phpdoc_tag_type` 会把它改成 `{@inheritDoc}` | 实测**两者对 phpcs 判定完全相同**（无冲突）；但 Squiz 不识别继承语义，故排除 `MissingReturn` / `MissingParamTag` |

### 6.4 禁止 `phpcbf`

`phpcbf` 是 phpcs 的写回工具，**本项目禁用** —— 它会与 fixer 对同一段代码反向修
（典型就是 long form ↔ short form 来回震荡）。

**排版只允许 `composer cs` 落地。**

## 7. 命令与门禁

### 7.1 命令清单

| 命令 | 归属 | 写文件 | 说明 |
|---|---|---|---|
| `composer analyse` | PHPStan | ❌ | `phpstan analyse --memory-limit=512M` |
| `composer baseline` | PHPStan | ✅ | 重新生成 baseline（**慎用**，见 4.3） |
| `composer cs:check` | fixer | ❌ | dry-run + diff |
| `composer cs` | fixer | ✅ | 落地排版（**唯一允许写文件的风格命令**） |
| `composer lint` | phpcs | ❌ | 完整审计；仅 error 影响退出码 |
| `composer lint:summary` | phpcs | ❌ | 按嗅探器聚合的汇总视图（看趋势用） |
| `composer lint:errors` | phpcs | ❌ | `--warning-severity=0`，只看错误 |
| `composer lint:self` | phpcs | ❌ | 自定义嗅探器自检（漂移检测 + 作用域/豁免矩阵） |
| `composer test` | PHPUnit | ❌ | 单元测试 |

### 7.2 建议执行顺序

```bash
composer lint && composer lint:self   # ① 只读审计（快，秒级）
composer analyse                      # ② 静态分析（改过代码先 clear-result-cache）
composer test                         # ③ 运行期验证
composer cs:check                     # ④ 排版体检
composer cs                           # ⑤ 需要落地时执行（会写文件）
# ⑥ 落地后再跑一遍 ①②③ —— 排版会打断读源码做结构断言的测试（见 §8.6）
```

### 7.3 不在 PHPUnit 套件内的校验脚本

`phpunit.xml` 只扫 `tests/Unit` 与 `client/tests/Unit`，以下脚本需单独执行，**退出码 0 = 全绿**：

```bash
composer test:frontend                                     # = node tests/Frontend/dashboard_autorefresh_check.js（面板自动刷新语义，注入假 DOM，无需服务端）
```

## 8. 工具引发的事故与守卫（重要）

本节记录两起**真实发生过**的「工具本身工作正常，却让门禁变红」的事故：

| 事故 | 触因 | 表现 | 为什么难查 |
|---|---|---|---|
| 混合行尾（8.1~8.5） | `git merge` 冲突消解 | 3 条 error，其中 2 条是假的 | **伪装成注释规范问题**，你会去改注释 |
| 排版落地打断结构断言（8.6） | `composer cs` 批量落地 | `composer test` 3 failures | 报的是测试失败，**根因在排版工具** |

两者有同一个教训：**门禁变红时，先问「最近有没有工具/合并改动了工作区」，再去看业务代码。**

### 8.1 现象

2026-09-22 一次 `git merge` 之后，`composer lint` 从 exit=0 变成 **exit=2**，报出 3 条 error：

```
start.php                             : line 2  [Squiz.Commenting.FileComment.SpacingAfterComment]
client/src/Error/ClientException.php  : line 2  [Squiz.Commenting.FileComment.SpacingAfterComment]
client/src/Error/ClientException.php  : line 3  [Squiz.Commenting.VariableComment.MissingVar]
```

外加 2 条 warning：`Internal.LineEndings.Mixed`。

**这 3 条里只有 1 条是真的**（`start.php` 的空行确实被 merge 消解吃掉了），
另外 2 条 error + 1 条 warning 都是**混合行尾导致的 PHPCS 判定错乱**。

### 8.2 根因

- 事故当时仓库**没有 `.gitattributes`**，`core.autocrlf=true`，`core.eol` 未设
  （**已于 2026-09-23 补上，见 §8.5**）
- `HEAD` 是一个 merge 提交，冲突文件正是 `start.php`
- 冲突消解时，git 把**重新生成的区域写成 LF**，而**未改动的区域保留原 CRLF 字节** → 文件变成混合行尾

两个文件的实测状态：

```
start.php                             286 行  CRLF= 96（第 1 行起）  LF=190（第 2 行起）
client/src/Error/ClientException.php  148 行  CRLF= 18（第 1 行起）  LF=130（第 2 行起）
```

全仓扫描（122 个 PHP 文件，已排除 `runtime/` `vendor/` `tests/Manual/_*`）：

```
纯 LF   : 120
纯 CRLF :   0
混合    :   2   ← 就是上面两个
```

即**工作区的事实约定是 LF**，这两个是 merge 留下的异类。

### 8.3 复现实验（定性结论）

把 `ClientException.php` 的原始内容复制两份，分别统一行尾后交给同一条 phpcs 命令：

| 样本 | 结果 |
|---|---|
| 原始（混合行尾） | 1 warning + 2 error |
| 统一 LF | **0 条** |
| 统一 CRLF | **0 条** |

**结论：只要行尾统一，那 3 条问题全部消失。**

混合行尾会让 PHPCS 的行号与「空行计数」错位，从而产出**指向注释的假阳性** —— 这是最坑的一点：
它伪装成注释规范问题，你会去改注释，而真正该改的是行尾。

### 8.4 处置

```bash
# 1) 两个文件统一为 LF（工作区多数派）
php -r 'foreach (["start.php", "client/src/Error/ClientException.php"] as $f) {
    file_put_contents($f, str_replace("\r\n", "\n", file_get_contents($f)));
}'

# 2) 补回 start.php 被 merge 吃掉的空行（文件头注释 */ 与 error_reporting 之间）

# 3) 复检
composer lint    # → exit=0（0 errors / 76 warnings）
```

### 8.5 两条候选守卫（均已实测）

#### 方案 A：phpcs 把「混合行尾」从 warning 提升为 error —— ✅ 实测有效

```xml
<rule ref="Internal.LineEndings.Mixed">
    <type>error</type>
</rule>
```

实测：同一样本从 `warning` 变成 `error`，退出码变 **2**。

**价值**：下次行尾再混，门禁**第一时间报出真正的原因**，
而不是让你去查那两条假的注释错误。

#### 方案 B：php-cs-fixer 的 `line_ending` —— ❌ 实测**无法**完全规整

在 `runtime/` 下建临时配置（复用 dist 规则 + 打开 `line_ending`）实测一个混合样本：

```
修复前: CRLF=7  LF=1   （混合）
修复后: CRLF=1  LF=7   （仍是混合！）
```

原因：`line_ending` 只处理 `T_WHITESPACE` token 的换行，
而 `<?php` 之后的换行被 **`T_OPEN_TAG` token 吞掉**，不受该规则管辖。

**所以不能靠 fixer 自愈混合行尾。**

`line_ending` 当前配置为 `false`（理由写的是「行尾统一交给 git」）。
本次事故说明这条理由**不完整**：git 只保证 *checkout* 时统一，不保证 *merge* 时统一。

#### 方案 C（根治方向）：`.gitattributes` —— ✅ 已于 2026-09-23 落地

**实施内容**（根目录 `.gitattributes`，此前不存在）：

```gitattributes
* text=auto

*.sh  text eol=lf      # shebang 带 \r 会 bad interpreter
*.php text eol=lf      # 项目约定工作区一律 LF（见 §8.7：混合行尾会造 phpcs 假阳性）

*.bat text eol=crlf    # 硬约束：CMD 按字节推进文件指针，多字节字符会错位
*.cmd text eol=crlf
*.ps1 text eol=crlf    # 硬约束：PowerShell 5.1 需 CRLF + UTF-8 BOM
```

**两个必须澄清的认知点**（实施时踩到，此前文档表述有误）：

1. **不能简写成 `* text=auto eol=lf`** —— 那会让 `bin/start.bat` / `bin/start.ps1` 在 Linux
   检出下变成 LF，而「两脚本必须 CRLF」是硬约束。**必须显式开 `eol=crlf` 例外**。
2. **`eol` 只管 checkout，索引用远是 LF。** `text` 属性下 git 从不把 CRLF 存进索引 ——
   所以此前 `bin/start.bat` 显示 `i/lf w/crlf` **不是缺陷**，也不存在「需要把索引改成 CRLF」这回事。
   真正的缺陷是：**CRLF 只靠本机 `core.autocrlf=true` 凑出来** —— 任何 Linux 检出、
   或 `autocrlf=input` / `false` 的克隆，拿到的都是 **LF 脚本**，硬约束跨机器不成立。

**决定性验证**（与 `core.autocrlf` 解耦，这是唯一能证明修复生效的实验）：

```bash
git config --local core.autocrlf false
rm bin/start.ps1 bin/start.bat
git checkout -- bin/start.ps1 bin/start.bat
tr -cd '\r' < bin/start.ps1 | wc -c   # → 895（全文 CRLF）
od -An -tx1 -N3 bin/start.ps1         # → ef bb bf（BOM 保住）
od -An -tx1 -N3 bin/start.bat         # → 40 65 63（`@ec`，无 BOM）
git config --local core.autocrlf true # 恢复
```

实测结果：`autocrlf=false` 下两个脚本**仍为 CRLF**、BOM 完好、与改前逐字节一致（`cmp` 通过）。

**`--renormalize` 是空操作（符合预期）**：`git add --renormalize .` 后变更清单只有本次的
代码改动与新文件，**两个脚本未进清单** —— 因为索引本来就是 LF，`eol=crlf` 只改 checkout 规则。
此前"索引会由 LF 变 CRLF"的预期**是错的**（见上面第 2 点）。

> ⚠ 本机现状观察（**已由上述修复解决**）：`git diff` 曾警告
> `LF will be replaced by CRLF the next time Git touches it` ——
> 即「下次 git 触碰这两个文件时会把它们转回 CRLF」，说明工作区行尾状态曾**依赖本机配置、不稳定**。
> 现在该行为由 `.gitattributes` 显式声明，与 `core.autocrlf` 无关。

### 8.6 事故二：排版落地打断「读源码做结构断言」的测试

`tests/Unit/` 里有一批测试**不执行被测代码，而是读源码做正则断言**
（`StartupBannerTest`、`LoggerTest::testTaskRunnerImplementsRunAtStart` 等）。
它们锁的是**时机与结构**——「横幅必须在 `Worker::runAll()` 之前打印」
「`log-archive` 必须在 `log-cleanup` 之前声明」「`run_at_start` 必须是单次延迟定时器」。
这类约束**无法靠运行期断言覆盖**，所以读源码是合理选择。

代价：**它们与排版工具直接耦合。** `2026-09-22` 的 `composer cs` 批量落地把锚点打散了：

| 文件 | 排版改动 | 断掉的用例 |
|---|---|---|
| `start.php` | `array('start', 'restart')` → `['start', 'restart']` | `StartupBannerTest` 的两条用例 |
| `src/Business/Task.php` | `! empty(` → `!empty(` | `LoggerTest::testTaskRunnerImplementsRunAtStart` |

结果：`composer test` 由绿转红（**3 failures**），而报错信息指向测试文件，
看不出真正动过手的是排版工具。

**处置：把锚点改成容忍两种等价写法，而不是钉死某一种。**

```php
// 同时接受 array(...) 与 [...]
"/in_array\(\\\$command, (?:array\('start', 'restart'\)|\\['start', 'restart'\\]), true\)/"

// 同时接受 `! empty(` 与 `!empty(`
'/^[ \t]*if \(!\s?empty\(\$job\[\'run_at_start\'\]\)\) \{$/m'
```

**理由**：这些用例锁的是**结构**，不是**排版**。按 §6.1 的判据，排版归 php-cs-fixer 独占 ——
测试就不该对排版有观点。否则「排版工具合法地改格式」会变成「门禁变红」，
而唯一的修法只能是不断追着改锚点。

> ⚠ **操作铁律**：**`composer cs` 落地后必须复跑 `composer test`。**
> §7.2 把 `composer cs:check` 排在最后、且在它之前先跑完 lint / analyse / test，
> 正是因为**落地排版之后要再跑一遍全部门禁**。

### 8.7 事故三：`composer cs` 自己会造出混合行尾

§8.1 的混合行尾来自 `git merge` 冲突消解。这一次来自**排版工具本身**，更隐蔽。

**现象**：在 CRLF 工作区执行 `composer cs` 之后，`composer lint` 由 `0 errors` 变成
**`exit=2 / 155 errors`**，且每个文件的首条告警都是 `File has mixed line endings`，
错误码是 §8.1 那两条的放大版（`SpacingAfterComment` / `VariableComment.MissingVar`）。

**根因**：`.php-cs-fixer.dist.php` 里 `line_ending => false`（理由写的是「行尾统一交给 git」）。
fixer 内部按 `\n` 重组，于是**被它改写的那些行落成 LF，未触碰的行保留原 CRLF** →
同一个文件两种行尾。实测：

```
src/Api/Bootstrap.php        1022 行  LF=1022  CR= 191   ← 混合
src/Common/RedisClient.php    975 行  LF= 975   CR= 155   ← 混合
src/Business/Router.php       170 行  LF= 170   CR=  20   ← 混合
```

可见 `line_ending => false` 的注释理由在**写入方向**上不成立：
git 只保证 checkout / merge 的**输入**行尾，不保证 fixer 的**输出**行尾。

**处置**：`composer cs` 之后必须把 PHP 文件统一回 LF，再复跑 `composer lint`。
本仓已按此口径把 **131 个 PHP 文件统一为纯 LF**（0 混合）；
`bin/start.bat` / `bin/start.ps1` 按项目硬约束**保持 CRLF**，统一时不得触碰。

### 8.8 事故四：把真实排版回归误诊为「行尾假象」

这条是**方法论教训**，代价最大。

level 6 补标注（`array` → `array<string, mixed>`）之后，`composer cs:check` 报 **41 文件待排版**。
当时据「40 个是 `w/crlf`、且被标记集合与 `w/crlf` 集合完全一致」判定为
**「100% 纯行尾假象」—— 这个结论是错的。**

统一行尾后重测，真实构成是：

| 原「41」的构成 | 数量 | 性质 |
|---|---|---|
| `StartupBannerTest.php` 的 `escape_implicit_backslashes`（`\(` → `\\(`） | 1 | 真实 |
| **`phpdoc_align` 对齐失效** | **33** | **真实** |
| 纯行尾差异 | 7 | 假象 |

**为什么会误诊**：改动过 docblock 的那批文件，恰好就是 `Edit` 保留了 CRLF 的那批
（见 `.workbuddy/memory/MEMORY.md`：`Edit` 保留原行尾，只有 `Write` 产出 LF）→
**「被标记集合」与「`w/crlf` 集合」完全重合**，形成一个用集合比对识破不了的完美共线。

**为什么会真的坏**：`phpdoc_align` 要求同一 docblock 内各 `@param` 的**变量名按列对齐**。
类型串从 `array`（5 字符）变成 `array<string, mixed>`（20 字符）后，兄弟行的对齐必须重算 ——
补标注时只替换了类型，没有重跑排版：

```diff
-     * @param int   $ttl    有效期（秒），0 取配置默认值
+     * @param int                  $ttl    有效期（秒），0 取配置默认值
```

**正确的判别手法**：不要拿「被标记集合」与「`w/crlf` 集合」比对（会被共线骗过），
而是**先把行尾统一，再跑 `composer cs:check`** —— 此时剩下的每一处都是真排版问题：

```bash
# 统一行尾之后...
composer cs:check     # 剩下的就是真实数量（本次为 33）
```

**收尾纪律**：**改过任何 docblock 的 tag 类型之后，必须跑一次 `composer cs` 并复跑 `composer test`。**
`@param` 类型变长 = `phpdoc_align` 必然失配；这与 §8.6 的铁律是同一条链上的两环。

> 本次修复规模：**33 个文件 / +275 −274 行**，其中 `git diff -w` 只剩 **1 处**
> （`RedisClient::get()` docblock 里 `phpdoc_separation` 补的一个空 `*` 行）
> → **全部改动都在注释 / 空白层，零运行期风险。**
>
> ⚠ 注意这一条同时说明：**`composer cs:check` 报 0 并不可信地代表「一直没问题」**。
> 它此前报 0，是因为批量排版落地过；补标注打破了它，而 41 个文件的假象又把它掩盖了一轮。

## 11. CI（GitHub Actions）

配置文件：**`.github/workflows/ci.yml`**（唯一入口）。

### 11.1 设计原则：CI 不发明第二套口径

workflow 里所有门禁都直接调用 `composer.json` 里已有的 script，**不在 YAML 里重写**
`php vendor/bin/phpstan ...` 这类命令。理由：一旦 CI 与本地命令不同，
出现「本地绿、CI 红」时就无法区分是**环境差异**还是**命令差异**。

### 11.2 三个作业（按依赖划分，不按快慢）

| 作业 | PHP | 外部依赖 | 跑什么 |
|---|---|---|---|
| `static` | 8.2（单版本） | 无 | `composer validate --strict --no-check-publish` → `analyse` → `lint` → `lint:self` → `cs:check` → `test:frontend` → `test:docs` |
| `test` | 8.2 / 8.3 / 8.4 / 8.5 矩阵 | 无 | `composer test` |
| `e2e` | 8.2 | **Redis 7 service + 全部 6 个角色** | `tests/e2e_check.php`（用例 A~P）→ `test:client-e2e` → `api_sign_check.js` → `demo:http` |

划分依据是**外部依赖**，不是耗时：

- `static` 固定单一 PHP 版本 —— phpstan / phpcs / fixer 的输出与「运行它们的 PHP 版本」无关
  （`phpstan.neon` 已用 `phpVersion: 80200` 锚定按 8.2 语义分析），跑 4 份只是重复消耗配额。
- `test` **不需要 Redis** —— `phpunit.xml` 明确只覆盖「纯函数 / 无 IO」组件，
  所以能在矩阵里裸跑（这是当年划定测试边界的直接收益）。
- `e2e` 需要真实端口与 Redis，故单列并挂 service container。

### 11.3 版本矩阵与 8.5 的「实验性」

依赖下限是 **PHP 8.2**，且它**不由项目代码决定，也不由运行时依赖决定**：
运行时（`workerman/workerman` 5.x 等）只要求 `>=8.1`，真正的抬升者是 **dev 工具链** ——
`friendsofphp/php-cs-fixer` 传递依赖的 `symfony/*` 7.x 要求 `>=8.2`，而 lock 是在 8.2 上解析的。
先前矩阵里的 8.1 腿因此连 `composer install` 都过不去（lock 中 8 个 symfony 包要求 `>=8.2`）。

矩阵覆盖 8.2~8.5，其中 **8.5 挂 `experimental: true`**（映射到 `continue-on-error`）：

phpunit 锁在 9.6（见 `phpunit.xml` 的版本说明），而 `phpunit.xml` 同时开了
`failOnWarning` / `failOnRisky` —— 8.5 上若冒出新的弃用告警会被直接判失败。
跑绿一段时间后再把 `experimental` 改成 `false`（**保留该键**，它是一条显式决定）。

矩阵用**纯 `include` 展开**而非「基矩阵 + include 补丁」：后者当 include 的键与基矩阵
同名时，「是覆盖还是新增」取决于 GitHub 的合并规则，写出来的组合容易与预期不符且难以自查。

### 11.4 触发分支为什么同时挂 main 与 master

本仓 GitHub **默认分支是 `main`**（`origin/HEAD -> origin/main`），
但**活跃开发实际推送在 `master`**（master 领先 `origin/main` 9 个提交）。
只挂 `main` 会让 CI 永不触发，PR 也默认指向 `main` —— 两个都挂才覆盖真实路径。

### 11.5 `e2e` 作业的几个关键细节

- **`needs: static`，刻意不依赖 `test`**：矩阵里 8.5 带 `continue-on-error`，
  而 `needs` 判定看的是作业**状态**而非「是否影响整体结论」—— 带上它会让 `e2e`
  在 8.5 变红时被静默 skip，反而丢掉最重的一条门禁。
- **`php start.php env:init`** 生成 `.env`（非交互，自动注入 `AUTH_SECRET` / `INTERNAL_SECRET`
  随机值）。`REDIS_HOST` / `REDIS_PORT` / `REDIS_DB` 经 job `env` 注入 —— 真实环境变量
  优先级最高（见 `.env.example` 的加载优先级说明），**无需改写 `.env`**。
- **`REDIS_DB=0`**：service container 每次都是全新实例，不存在本机那种 DB0 历史残留
  （本机才用 DB 9）。
- **启动用 `bin/start.sh start`，不要用 `bin/dev/boot_all.sh`**：前者守护化（`-d`）
  并做 preflight 与 pid 就绪轮询；后者是开发期编排，末尾 `wait` 常驻，在 CI 里会占住步骤直至 timeout。
- **补一次端口级就绪确认**：`start.sh` 只轮询 pid 文件，而 pid 出现 ≠ 端口 bind 完成。
  TCP 走 `/dev/tcp`（`1238` / `8282` / `8290` / `8291`）；**UDP 8283 没有 TCP 监听**，
  只能查 `ss -lun`。
- **e2e 传入 run 级唯一 uid**（`e2e-{run_id}-{run_attempt}`）：UDP 无断连事件，其会话
  不因客户端退出而在 Redis 中失效，复用同一 uid 会把上一轮残留会话判成在线，
  污染离线补投用例（K）。
- **失败时上传 `runtime/logs/` 为 artifact** —— 端到端失败最耗时的环节就是拿日志。
- `tests/Api/api_sign_check.js` 只用 Node 内置模块（`fs` / `path` / `crypto` / `http`），
  **无需 `npm install`**；`tests/Api/http_demo.php` 需要 **ext-curl**（它不在 `composer.json`
  的 `require` 里，故 CI 的扩展清单里要显式加上）。

### 11.6 CI 上的 `cs:check` 反而比本地可信

CI 检出是 **LF**（git 索引侧本就是 LF），因此 `composer cs:check` 在 CI 上**恒应为 0 文件**，
**一红就是真的排版违规**。而本机因 `core.autocrlf=true` 工作区是 CRLF，
同一条命令会混入行尾噪声，甚至（如 §8.7 所述）掺进 fixer 自造的混合行尾 ——
本地结果必须按 §8.8 的方法**先统一行尾再解读**。

### 11.7 本机无法验证的部分（已知边界）

`e2e` 作业依赖 Linux 守护化启动与 Redis service container，本机（Windows）无法复现，
是本 workflow 中最可能在**首次运行**时仍需微调的部分。
`static` / `test` 两个作业用到的每一条命令都已在 2026-09-22 逐条本机复跑验证。

### 11.8 PHP 下限提升：连锁改动清单

2026-09-22 把下限由 **8.1 抬到 8.2**（这是本项目第三次做同类操作，前两次为 8.0→8.1）。
下限**不写在一个地方**，漏改就会出现「声明是 8.2、某处仍按 8.1 判定」的静默不一致：

| # | 位置 | 说明 |
|---|---|---|
| 1 | `composer.json` → `require.php` | 声明的真源 |
| 2 | `composer.lock` | 用 `composer update --lock` 刷新 `platform.php` 与 `content-hash`；**手改 lock 会让 `composer validate --strict` 失败** |
| 3 | `phpstan.neon` → `phpVersion` | `80100` → `80200`。**改这里会牵动 baseline 失配**，见 §10 与下方第 1 条 |
| 4 | `config/app.php` → `runtime.php_min` | 启动脚本版本预检的唯一真源 |
| 5 | `bin/start.sh` / `bin/start.ps1` | 两者各自的**回落值** `8.1.0`/`80100` → `8.2.0`/`80200` —— 解析配置失败时使用（**当前已是 8.2**） |
| 6 | 全量源文件头注释 | 「兼容 PHP x.y ~ 8.5」，本次 **107 个文件**（`src` / `client` / `tests` / `config` / `start.php`） |
| 7 | `src/Common/Logger.php` | 「不使用 8.2+ 独有语法」→ 「不使用 8.3+ 独有语法」 |
| 8 | `.github/workflows/ci.yml` | 矩阵起点（本次 8.1 腿整条移除） |
| 9 | 文档 | `README.md`（§4 版本表 / §6.7 / §13.1 / §13.2 / §13.3 / §13.7）、`AGENTS.md` §3 §4、本文件 |

**抬升后必须复跑的三件事** —— 三件都能捕获「声明与行为不一致」：

1. `composer analyse` —— `phpVersion` 变更会让部分冻结条目报 `ignore.unmatched`
   （本次实测：`@throws Random\RandomException` 那条，生产侧 baseline 9 → 8 条）；
2. `composer cs:check` —— `@auto` 的迁移规则集**由 PHP 下限推导**（§2.2），下限一改规则集就变
   （本次实测仍为 `0 of 120 files`，即现有代码无需因抬升而改写，但必须跑一次才能下这个结论）；
3. `composer validate --strict` —— 验证 lock 与 `composer.json` 已同步（`content-hash`）。

> **下限由谁决定，要查清再写进注释。** 本次抬升**不是**代码或运行时依赖所迫：
> `workerman/workerman` 5.x 只要求 `>=8.1`，真正的抬升者是 **dev 工具链**
> （`friendsofphp/php-cs-fixer` → `symfony/*` 7.x 要求 `>=8.2`，而 lock 是在 8.2 上解析的）。
> 照抄「下限由 workerman 决定」会写出一条误导后人的注释 —— 与 §8 的事故同一性质：
> **看起来在描述约束，实际只是复述了一个巧合。**
